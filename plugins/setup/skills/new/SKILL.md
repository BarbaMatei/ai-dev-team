# New project setup

You start a web project so that its first working session goes to its first feature, not to plumbing. You ask, show one list, and write only after the owner's yes. You never write application code and never choose the stack: specsmd's project-init does.

- **Scripts:** `<scripts>` = `<base directory of this skill>/../../scripts` (Claude Code prints "Base directory for this skill: ..." when this skill loads). Run them from the project root.
- **Read beside this file:** `interview.md` before step 2, `first-feature.md` before step 9.
- **Work folder:** `<work>` = `<OS temp folder>/ai-dev-team-setup/<project folder name>`: `answers.json`, `staging/`, `list.md` and `state.json` (`{ "step": <n>, "kind": "new" | "existing" }`, rewritten after each step). If `state.json` exists when you start, say which step it stopped after, trust its `kind` (specsmd's files make a new folder look like an existing repository) and resume at the next step.

## Rules that never bend

1. Nothing of the setup is written in the project, and nothing on GitHub changes, before the owner's yes on the full list (step 6). specsmd's files are the owner's own run.
2. An existing file is never overwritten silently: each `differs` file is shown with its difference and asked about on its own.
3. Never store a secret, never run `gh secret`, never run the release-key script: hand the owner the ready command and say in one line what it does.
4. One question per message, plain words. Never merge.

## Steps

1. **Detect** (a resumed run skips this step). `git rev-parse --show-toplevel` (a folder above the project does not count: then it is not a repository yet), `git remote get-url origin`, `.claude/ai-dev-team.json`.
   - A `setup` key in that file → the project is set up: use `setup:check` instead and stop.
   - No files except dot-folders → `kind` new (`git init` waits for step 7).
   - Anything else → `kind` existing: list in a few lines what is there (code folders, `memory-bank/`, kit config, workflows). `git status --porcelain` not empty → ask the owner to commit or stash their work first, so the setup commit holds nothing of theirs. No `origin` → the setup goes straight onto `main` as for a new project (ask before `git branch -m main` if the branch has another name). With an `origin` it goes through a PR, and the default branch must be `main` (the workflows release from it): `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` prints another name → ask the owner to rename it on GitHub (Settings, Branches) and wait.
   `gh auth status` fails → hand the owner `gh auth login` and wait.
2. **Interview** (`interview.md`).
3. **specsmd.** `memory-bank/standards/` exists → no install and no init; offer one review of those standards, then go on. Otherwise hand the owner, for Command Prompt: `cd /d "<project>" && npx specsmd@latest install` (macOS or Linux: `cd "<project>" && npx specsmd@latest install`); they pick Claude Code and the AI-DLC flow. Once `.specsmd/aidlc/` exists, read `.specsmd/aidlc/skills/master/project-init.md` and follow it here, in this session: first tell it the purpose, the users and the must-do from the interview; its own questions (project type, stack, data, coding rules, UI) are the ones the kit leaves to it. Go on when it reports completion and `memory-bank/project.yaml`, `standards/tech-stack.md` and `standards/coding-standards.md` exist.
4. **Parts.** From `standards/tech-stack.md`, list each part with its role (`api`, `web` or `lib`, at most one of each), folder and stack id: `dotnet`, `angular`, `node` (Vite, React, Vue, NestJS), `python`. A part whose folder the standards do not name → ask for it (default: `api`, `web`, `lib`). A part that fits no id → one question: its scoped test command and folder; leave it out of `stacks` (step 5 adds its test command; its CI job is the owner's). Releases: the whole repository ships under one version (an API and its own front end released together count as one) → `semantic-release`; packages released to others separately (libraries, plugins) → `kit`, with `releaseRef` = the newest release tag of the kit's release plugin: `gh api repos/BarbaMatei/ai-dev-team/git/matching-refs/tags/release-v --jq ".[].ref" | sed "s#refs/tags/##" | sort -V | tail -n 1` (in Bash).
5. **Render.** Write `<work>/answers.json`, for example:
   ```json
   { "name": "plant-swap", "language": "English", "owner": "octo", "ownerType": "User", "visibility": "private",
     "stacks": [{ "id": "dotnet", "dir": "api", "role": "api" }, { "id": "angular", "dir": "web", "role": "web" }],
     "release": "semantic-release", "purpose": "...", "users": "...", "mustDo": "..." }
   ```
   Delete `<work>/staging` if it exists, then `node "<scripts>/render.mjs" <work>/answers.json <work>/staging`. In the staged `CLAUDE.md`, replace each `<!-- setup:fill ... -->` comment with what it asks for, from the standards: short bullets, the commands section using the same scoped test commands as `tests` in the staged `.claude/ai-dev-team.json`, where-to-read as a two-column table. A part left out in step 4: add its test command to the staged `tests` under its role. With an `origin`: set the staged `metrics.since` to the newest PR number (`gh pr list --state all --limit 1 --json number`) plus one.
6. **The list.** Run `node "<scripts>/apply.mjs" <work>/staging` and `node "<scripts>/github.mjs" plan <work>/answers.json`. Write one message, and save it without its closing question as `<work>/list.md`:
   - files to create, grouped (AI setup, CI and secret scan, releases, GitHub, editor), one plain line each;
   - files that exist and differ, each with what would change;
   - the GitHub steps in plain words. A `protection` line ending `(private: needs a paid plan)` → "GitHub refuses to protect main on a private repository on the free plan; then releases push with the built-in token and no release key is needed"; ending `(only if the kit's ci.yml is used)` → main is protected only if the project's `ci.yml` is replaced by the kit's, because the protection waits for the kit's CI checks;
   - what the owner will run themselves: the release key (a `release-key` line), a `GITLEAKS_LICENSE` for an organization (free key from gitleaks.io, then `gh secret set GITLEAKS_LICENSE`), the CI job of a part left out in step 4.
   End with "Set this up?". Anything but yes → stop; nothing was written.
7. **Write.** `kind` new: `git init -b main`, then `git symbolic-ref HEAD refs/heads/main` (an existing empty repository keeps its old branch name otherwise). With an `origin`: `git switch -c chore/kit-setup` first, or `git switch chore/kit-setup` when `git branch --list chore/kit-setup` prints it (specsmd's uncommitted files come along). Never switch a checkout other sessions use: ask the owner to close them first. Then `node "<scripts>/apply.mjs" <work>/staging --write`. `hooksPath kept <value>` → the project already uses another hook manager: tell the owner the kit's `.githooks/pre-commit` runs only once their manager calls it. For each `differs` file, one message with the difference and "Replace, merge or keep?": replace = copy the staged file over it; merge = `.claude/ai-dev-team.json` gets the staged `setup` key and only the keys it lacks, `.claude/settings.json` gets the marketplace and the plugins it lacks, `.gitignore` gets the lines it lacks, `CLAUDE.md` gets the kit blocks it lacks where they fit; the owner's text stays untouched.
8. **Commit and GitHub.** The git hook needs the kit's guardrails plugin: `<Claude config folder>/plugins/cache/ai-dev-team/guardrails/` missing (`CLAUDE_CONFIG_DIR`, else `~/.claude`) → hand the owner `claude plugin install guardrails@ai-dev-team --scope project` and `claude plugin install metrics@ai-dev-team --scope project`, and wait. `git add -A`, `git add --chmod=+x .githooks/pre-commit`, commit `chore: set up the AI workflow, CI, secret scan and releases`. The guardrails pre-commit lists comment lines in specsmd's own scripts: when every listed line is under `.specsmd/`, repeat the commit with `COMMENTS_OK=1` for that commit only and say so in the report; any other listed line → show it and stop. Then `node "<scripts>/github.mjs" apply <work>/answers.json`: without an `origin` it creates the repository and pushes `main`; then labels, protection and the key script; one result line each. Exit 1 → show its line; once the cause is fixed, run it again (it skips what is done). With an `origin`: `git push -u origin chore/kit-setup` and `gh pr create --body-file <work>/list.md`. A `release-key <path>` line → hand the owner `"C:\Program Files\Git\bin\bash.exe" "<path>"` (Command Prompt; macOS or Linux: `bash "<path>"`): it makes a write deploy key and stores its private half as the `RELEASE_DEPLOY_KEY` secret. `protection unavailable: …`, `protection skipped: …` or `release-key skipped: …` → main stays unprotected; releases use the built-in token.
9. **Report, then the first feature.** One message: what is set up (one line per group), what is left to the owner, which GitHub limits applied. Then `first-feature.md`. Delete `<work>` once the owner has picked.
